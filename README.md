# QazMeeting AI

Прототип системы автопротоколирования совещаний для HackAlem AI (владелец кейса: Самрук-Қазына).

## Проблема и целевая аудитория

Протоколы совещаний часто фиксируются вручную. Из-за этого поручения, сроки и ответственные могут теряться или искажаться. Целевая аудитория MVP — секретари совещаний, руководители и кураторы поручений.

## Целевой сценарий MVP

1. Пользователь загружает аудиозапись совещания.
2. Локальный модуль speech-to-text строит транскрипт на русском, казахском или смешанной речи.
3. Модуль диаризации разделяет реплики по говорящим.
4. Meeting Protocol Agent анализирует транскрипт и извлекает поручения.
5. Для каждого поручения сохраняются ответственный, срок, evidence-фрагмент и признак необходимости ручной проверки.
6. Формируется краткое управленческое саммари.
7. Пользователь просматривает результат и экспортирует итоговый протокол в DOCX.

## Обязательные требования кейса

- распознавание речи участников;
- русский язык;
- казахский язык;
- смешанная русско-казахская речь;
- диаризация;
- поручения с ответственным и сроком;
- итоговое саммари;
- экспорт протокола в DOCX/PDF.

## Приватность

Кейс требует возможности работы в закрытом контуре: аудио и текст совещания не должны передаваться во внешние облачные API.

Поэтому финальный demo-пipeline проектируется local-first/self-hosted.

У команды есть ключи OpenAI и NVIDIA. Ограничение кейса запрещает отправлять аудио и текст совещания в их облачные API, поэтому эти ключи не входят в путь обработки MVP. Модель для анализа транскрипта запускается локально (например, через Ollama). Секреты не коммитятся в Git.

## Контракт данных

Основные модели находятся в `app/models/schemas.py`:

- `TranscriptSegment` — одна реплика с таймкодами и speaker id;
- `ActionItem` — поручение с ответственным, сроком и evidence;
- `SpeakerInfo` — соответствие speaker id и предполагаемого имени;
- `MeetingResult` — итог анализа одного совещания;
- `AgentEvent` — журнал этапов работы агента.

Это общий контракт между тремя ветками разработки.

## Meeting Protocol Agent

Оркестратор находится в `app/agents/meeting_agent.py`.

В ветке `feature/agent` реализован агент с локальным Ollama, проверкой evidence, нормализацией сроков, обработкой отмен и дедупликацией поручений. Последовательность обработки:

```text
Transcript
   |
   +--> speaker resolver
   +--> task extractor
   +--> deadline normalizer
   +--> validator
   +--> summarizer
   |
   v
MeetingResult
```

Архитектура специально допускает замену конкретной локальной модели без изменения UI и STT-pipeline.

Запуск локального агента:

```bash
ollama pull qwen2.5:3b-instruct-q4_K_M
ollama serve
export OLLAMA_MODEL=qwen2.5:3b-instruct-q4_K_M
```

Эта модель указана в настройках актуального агента. Другую локальную модель
можно выбрать переменной `OLLAMA_MODEL`; результаты ниже относятся только к
фактически испытанным моделям.

```python
from app.agents import MeetingProtocolAgent

result = MeetingProtocolAgent().run(transcript, meeting_date, title)
```

Агент обращается только к `127.0.0.1`/`localhost`, запрашивает структурированный
JSON и затем независимо проверяет каждое поручение по существующему
`segment_id`. Evidence и таймкоды всегда берутся из исходного
`TranscriptSegment`, а не из текста модели. Несуществующие сегменты и пустые
задачи отбрасываются. Если Ollama недоступна или ответ невалиден, исходный
транскрипт сохраняется, а неподтверждённые поручения не добавляются.

## Материалы кейса и регрессионная проверка

Описание кейса, эталонные протоколы, manifest аудиозаписей и ожидаемые
поручения находятся в `case_materials/`. MP3 остаются во внешнем хранилище и
не коммитятся. Проверка агента на подготовленном JSON-транскрипте:

```bash
python scripts/evaluate_agent.py \
  /path/to/meeting_2_transcript.json \
  case_materials/expected/meeting_2.json \
  --meeting-date 2026-09-23 \
  --title "Совещание №2" \
  --timeout 300
```

Проверено 23 сентября 2026 года на Apple Silicon, 16 GB RAM, полностью
локально. Входные JSON-транскрипты были получены из предоставленных MP3;
в Git они и отчёты с полным текстом не добавлены.

- Актуальный строгий агент с `qwen3:1.7b`, совещание №2: 124 с,
  0/5 обязательных ожиданий; единственный кандидат отвергнут как
  не подтверждённый выбранным evidence.
- `qwen3.5:9b-mlx`, совещание №2: запросы с лимитом 120 и 300 с
  завершились безопасным fallback без поручений.
- `pytest -q`: 77 passed, 1 skipped. Рекомендуемая в конфигурации модель
  `qwen2.5:3b-instruct-q4_K_M` на этих MP3 пока не проверена.

Оценка требует совпадения действия, исполнителя и срока. В эталоне совещания
№1 есть расхождения с буквальным STT (например, Павлодар против Атырау);
на актуальном строгом агенте это совещание ещё не прогонялось. Диаризация в
проверенном прогоне была недоступна:
входные сегменты имеют `speaker_id="UNKNOWN"`; агент не выдаёт их за
установленные личности.

## Сборка трёх веток

Каждый участник сначала подтягивает актуальный `main` в свою ветку и использует `app/models/schemas.py` как единый контракт. Не копируйте схемы по веткам и не меняйте публичные поля без согласования. Подключаемые интерфейсы:

```python
# feature/audio
process_audio(audio_path: str) -> list[TranscriptSegment]
# feature/agent
MeetingProtocolAgent().run(transcript, meeting_date, title) -> MeetingResult
# feature/ui
build_docx(result: MeetingResult) -> bytes
```

При падении диаризации транскрипция должна сохраниться с `speaker_id="UNKNOWN"` и предупреждением. Если локальная LLM не вернула проверяемый ответ, показываем предупреждение и исходный транскрипт: недоказанные поручения не включаем. Каждое поручение должно иметь фрагмент подтверждения, а неуказанные исполнитель и срок остаются `null`. Пустой срок не означает ошибку распознавания: пользователь видит его в таблице.

Для финальной проверки запускаем настоящий путь **MP3 → транскрипт → говорящие → поручения → саммари → DOCX**, затем проверяем отдельно русский, казахский и смешанную речь. Примеры `Совещание №1/№2` служат тестовыми данными вне репозитория. В совещании №2 особенно проверяем поручение Ерлану до конца недели, поиск альтернативного поставщика Ботагоз Нурлановной за две недели и поручения Салтанат Ерболовне без названного срока. Автоматическая разметка говорящих не равна достоверному установлению их имён: сомнительные имена требуют ручной проверки.

В ветке `feature/agent` тесты проверяют общий контракт, конфигурацию, обработку ответов модели, evidence, сроки, отмену поручений и локальный HTTP-транспорт. Они **не доказывают**, что аудио, настоящая модель агента или экспорт уже работают.

## Проверка агента в `feature/agent`

Запускайте тесты из корня репозитория:

```bash
python -m pytest -q
```

Для проверки настоящей модели отдельно установите и запустите Ollama и скачайте модель `qwen2.5:3b-instruct-q4_K_M` (или укажите установленную модель через `OLLAMA_MODEL`). Затем в PowerShell:

```powershell
$env:RUN_OLLAMA_INTEGRATION = "1"
python -m pytest tests/test_meeting_agent.py::test_real_ollama_smoke -q
```

Без этой переменной интеграционный тест пропускается. `OLLAMA_BASE_URL` принимает только HTTP-адрес loopback (`127.0.0.1`, `localhost`, `[::1]`), без учётных данных, query и fragment. HTTP-прокси из окружения и перенаправления отключены.

Параметры читаются из переменных окружения: файл `.env` сам по себе не загружается. Например, `$env:OLLAMA_MODEL = "qwen2.5:3b-instruct-q4_K_M"` в PowerShell. Если модель недоступна, агент сохраняет транскрипт и возвращает предупреждение без выдуманных поручений.
