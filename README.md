# QazMeeting AI — протокол совещания из аудиозаписи

Прототип для кейса HackAlem AI от Самрук-Қазына. Цель — помочь команде не
терять решения и поручения после совещаний на русском и казахском языках.

> **Для жюри: это прототип в разработке, а не готовый сервис.** В ветке
> `feature/audio` реально работает локальное распознавание MP3/WAV с
> таймкодами. Надёжная диаризация, качество извлечения поручений и общий
> сценарий до итогового DOCX пока не подтверждены.

## За минуту: проблема, решение и результат

**Проблема.** Протоколы часто составляют вручную после встречи. В длинной или
смешанной русско-казахской речи можно пропустить поручение, перепутать
исполнителя или срок. Потом трудно проверить, где именно в разговоре прозвучало
решение. При этом материалы совещаний могут быть конфиденциальными.

**Наш подход.** Пользователь загружает MP3/WAV → локальное распознавание
возвращает реплики с таймкодами → диаризация пытается разделить говорящих →
агент извлекает поручения, ответственных и сроки, привязывая каждое поручение
к исходной реплике → человек проверяет результат и скачивает протокол.
Основной путь задуман для работы на своём компьютере без передачи аудио и
транскрипта во внешние AI API.

**Что показано на реальных данных.** На MacBook Air M4 запись
«Совещание №1.mp3» дала 81 распознанную реплику с таймкодами за 17,04 с при
повторном запуске с моделью в кэше. Например, первая реплика занимает
`00:00–00:14.94`, следующая — `00:15.38–00:29.98`. Говорящие остались
`UNKNOWN`: модель диаризации не была доступна локально. Это не подтверждение
точности текста или имён говорящих.

| Часть сценария | Проверенный статус |
| --- | --- |
| MP3/WAV → текст с таймкодами | Работает локально на реальном MP3; 81 сегмент за 17,04 с при повторном запуске. |
| Определение говорящих | Реализован безопасный fallback `UNKNOWN`; качество реальной диаризации не проверено. |
| Поручения и саммари | Агент разрабатывается в `feature/agent`. Проверка версии `da47efa` на этом транскрипте дала 0 из 8 обязательных поручений по эталону; улучшения в более новых коммитах здесь не проверялись. |
| UI и DOCX | Разрабатываются в `feature/ui`; общий путь от MP3 до DOCX в этой ветке не проверен. |
| Облачная проверка | Не часть локального сценария. OpenAI на тестовом запросе ответил HTTP 429; успешный облачный результат не подтверждён. |

**Что остаётся до демонстрации полного MVP:** получить и проверить модель
диаризации; повысить качество агента на эталонных поручениях; объединить три
ветки и провести один сквозной тест `MP3 → транскрипт → поручения → DOCX`;
отдельно проверить казахскую и смешанную речь. Ни один из этих пунктов не
считается выполненным только потому, что есть отдельный модуль или unit-тест.

## Проблема и целевая аудитория

Протоколы совещаний часто фиксируются вручную. Из-за этого поручения, сроки и ответственные могут теряться или искажаться. Целевая аудитория MVP — секретари совещаний, руководители и кураторы поручений.

## Целевой сценарий MVP

1. Пользователь загружает аудиозапись совещания.
2. Локальный модуль speech-to-text строит транскрипт на русском, казахском или смешанной речи.
3. Модуль диаризации разделяет реплики по говорящим.
4. Meeting Protocol Agent анализирует транскрипт и извлекает поручения.
5. Для каждого поручения сохраняются ответственный, срок, evidence-фрагмент и признак необходимости ручной проверки.
6. Формируется краткое управленческое саммари.
7. Пользователь просматривает результат и экспортирует итоговый протокол в DOCX.

## Целевые требования кейса (не все реализованы)

- распознавание речи участников;
- русский язык;
- казахский язык;
- смешанная русско-казахская речь;
- диаризация;
- поручения с ответственным и сроком;
- итоговое саммари;
- экспорт протокола в DOCX/PDF.

## Приватность

Кейс требует возможности работы в закрытом контуре. Основной путь обработки
аудио остаётся локальным и не использует внешние AI API.

Поэтому финальный demo-пipeline проектируется local-first/self-hosted.

Для отдельной проверки MVP можно явно включить облачную транскрипцию OpenAI.
Она отправляет выбранный аудиофайл провайдеру, поэтому применяйте её только к
данным, для которых разрешена такая передача. Ключи не коммитятся в Git.

## Контракт данных

Основные модели находятся в `app/models/schemas.py`:

- `TranscriptSegment` — одна реплика с таймкодами и speaker id;
- `ActionItem` — поручение с ответственным, сроком и evidence;
- `SpeakerInfo` — соответствие speaker id и предполагаемого имени;
- `MeetingResult` — итог анализа одного совещания;
- `AgentEvent` — журнал этапов работы агента.

Это общий контракт между тремя ветками разработки.

## Meeting Protocol Agent

Контракт агента находится в `app/agents/meeting_agent.py`. В этой ветке это
ещё интерфейс с `NotImplementedError`; отдельная ветка `feature/agent`
содержит исполняемую реализацию с локальной моделью Ollama и проверкой evidence.
Однако наличие реализации не означает достаточного качества: проверка версии
`da47efa` на реальном транскрипте совещания №1 не подтвердила ни одного из
восьми обязательных поручений. Планируемая последовательность:

```text
Transcript
   |
   +--> speaker resolver
   +--> task extractor
   +--> deadline normalizer
   +--> validator
   +--> summarizer
   |
   v
MeetingResult
```

Архитектура специально допускает замену конкретной локальной модели без изменения UI и STT-pipeline.

## Разделение команды

- `feature/audio` — Audio / STT / diarization;
- `feature/agent` — Meeting Protocol Agent / extraction / validation / summary;
- `feature/ui` — Streamlit / DOCX / integration;
- `main` — общий контракт и место для интеграции; полный сценарий пока не проверен.

## Локальное распознавание аудио

Публичная точка интеграции для UI и агента:

```python
from app.services.audio import process_audio

segments = process_audio("/path/to/meeting.mp3")
```

`process_audio(audio_path: str) -> list[TranscriptSegment]` принимает MP3/WAV и
использует ровно `TranscriptSegment` из `app/models/schemas.py`. На Apple
Silicon распознавание выполняет локальный multilingual Whisper через MLX;
русский, казахский и смешанная речь не ограничиваются принудительно одним
языком. Имена говорящих не угадываются и остаются `None`.

Установка под Python 3.11:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements-audio.txt
```

Первый запуск загружает STT-модель `mlx-community/whisper-small-mlx-q4` в
локальный кэш. Модель можно заменить локальным каталогом или другим MLX
checkpoint через `AUDIO_STT_MODEL`. Значение `AUDIO_LANGUAGE=ru` или `kk`
допустимо только когда язык заранее достоверно известен; без него Whisper
работает в режиме автоматического multilingual-распознавания.

Диаризация выполняется локально моделью
`pyannote/speaker-diarization-community-1`. Для её первоначальной загрузки
нужно один раз принять условия модели в Hugging Face и передать `HF_TOKEN`,
либо скачать модель заранее и установить путь в `AUDIO_DIARIZATION_MODEL`.
Само аудио и транскрипт во внешние API не отправляются; телеметрия pyannote
отключена. По умолчанию диаризация работает на CPU для совместимости с macOS;
устройство можно явно задать через `AUDIO_DIARIZATION_DEVICE`.

Если зависимость или модель диаризации недоступна, распознавание не теряется:
функция выдаёт `RuntimeWarning`, пишет причину в журнал и возвращает сегменты с
`speaker_id="UNKNOWN"`. Это честный fallback, а не идентификация человека.

Smoke test на реальном файле вне Git:

```bash
python scripts/smoke_audio.py "/path/to/Совещание №1.mp3" \
  --limit 8 --output output/meeting_1_transcript.json
```

Скрипт печатает длительность обработки, число сегментов, найденные speaker id и
несколько реплик с таймкодами. `--output` сохраняет полный JSON-транскрипт в
игнорируемый каталог `output/`. Аудиозаписи, модели и токены исключены из Git
через `.gitignore`; не добавляйте их принудительно.

## Отдельная облачная проверка аудио

Ссылка на проект OpenAI не содержит API‑ключ. Создайте ключ в проекте и задайте
`OPENAI_API_KEY` в окружении или в игнорируемом `.env`. Скрипт не читает `.env`
автоматически: если используете файл, экспортируйте переменную перед запуском.

```bash
export OPENAI_API_KEY="<ключ>"
python scripts/smoke_audio_cloud.py "/path/to/meeting.mp3" \
  --allow-cloud-upload --limit 8 --output output/cloud_transcript.json
```

Эта команда использует OpenAI `gpt-4o-transcribe-diarize` с
`diarized_json` и `chunking_strategy=auto`, возвращая тот же
`TranscriptSegment` с таймкодами и speaker id. Имена и язык не угадываются.
Файл из `--output` содержит полный транскрипт; `output/` исключён из Git.
Без `--allow-cloud-upload` аудио не отправляется. Публичный
`process_audio(...)` и локальный smoke test остаются без облачных вызовов.

Ссылка NVIDIA Brev ведёт к биллингу и GPU‑кредитам. Это не ключ inference.
Для NVIDIA API Catalog нужен отдельный `NVIDIA_API_KEY`; `BREV_API_KEY` нужен
только для автоматизации Brev CLI. В этой ветке нет неподтверждённого
NVIDIA‑STT backend: Brev можно использовать для запуска будущего локально
развёрнутого сервиса на GPU, когда будет известен его endpoint.

## Текущий статус

На `main` есть общие Pydantic-схемы и интерфейсы. В `feature/audio` публичная
функция `process_audio` проверена на настоящем «Совещание №1.mp3»: 81 сегмент
с таймкодами. Первый запуск с загрузкой модели занял 101,5 с; повторные
запуски с моделью в кэше — 16,23 и 17,04 с на MacBook Air M4.

При отсутствии доступа к модели pyannote транскрипт сохранился с
`speaker_id="UNKNOWN"` и предупреждением. Никакие имена говорящих не
определялись. Запись преимущественно с русской речью обработана; отдельной
оценки качества казахской и смешанной речи пока нет.

Агент из `feature/agent` отдельно запускался на этом транскрипте, но проверка
версии `da47efa` дала 0/8 обязательных поручений по эталону. Это означает,
что автоматический протокол без ручной проверки сейчас ненадёжен. Ветки агента
и UI/DOCX не объединены с `feature/audio`; сквозной путь не заявляется как
готовый. Попытка облачной транскрипции OpenAI получила HTTP 429 на полном и
коротком аудиофайле; причина 429 не установлена, успешного облачного теста нет.

## Автоматические тесты этой ветки

```bash

```

На последнем запуске — 11 пройденных тестов. Они проверяют контракт и
обработку ошибок, но не заменяют оценку качества распознавания или поручений.

## Данные и внешние сервисы

Для демонстрации используются предоставленные организаторами тестовые записи
совещаний. Полноценная проверка смешанной русско-казахской речи ещё требуется.

Внешние AI API не являются частью допустимого финального processing path для аудио/текста совещания из-за требования закрытого контура.
Дополнительный OpenAI smoke test предназначен только для отдельной облачной
проверки при явно разрешённой передаче конкретного аудио.

## Ограничения текущего состояния

- production-интеграция с Teams/Zoom/Google Meet не реализована;
- интеграция с СЭД не входит в обязательный MVP;
- voice biometric identification не входит в обязательный MVP;
- количественная оценка точности STT, диаризации и агента, а также полный
  end-to-end тест ещё требуются; отдельные результаты выше — не такая оценка.

## Сборка трёх веток

Каждый участник сначала подтягивает актуальный `main` в свою ветку и использует `app/models/schemas.py` как единый контракт. Не копируйте схемы по веткам и не меняйте публичные поля без согласования. Подключаемые интерфейсы:

```python
# feature/audio
process_audio(audio_path: str) -> list[TranscriptSegment]
# feature/agent
MeetingProtocolAgent().run(transcript, meeting_date, title) -> MeetingResult
# feature/ui
build_docx(result: MeetingResult) -> bytes
```

При падении диаризации транскрипция должна сохраниться с `speaker_id="UNKNOWN"` и предупреждением. Если локальная LLM не вернула проверяемый ответ, показываем предупреждение и исходный транскрипт: недоказанные поручения не включаем. Каждое поручение должно иметь фрагмент подтверждения, а неуказанные исполнитель и срок остаются `null`. Пустой срок не означает ошибку распознавания: пользователь видит его в таблице.

Для финальной проверки запускаем настоящий путь **MP3 → транскрипт → говорящие → поручения → саммари → DOCX**, затем проверяем отдельно русский, казахский и смешанную речь. Примеры `Совещание №1/№2` служат тестовыми данными вне репозитория. В совещании №2 особенно проверяем поручение Ерлану до конца недели, поиск альтернативного поставщика Ботагоз Нурлановной за две недели и поручения Салтанат Ерболовне без названного срока. Автоматическая разметка говорящих не равна достоверному установлению их имён: сомнительные имена требуют ручной проверки.

Тест `pytest -q` не доказывает качество аудио, агента или экспорта. Реальные
результаты и ограничения перечислены в начале README.
