# QazMeeting AI

Прототип системы автопротоколирования совещаний для HackAlem AI (владелец кейса: Самрук-Қазына).

## Проблема и целевая аудитория

Протоколы совещаний часто фиксируются вручную. Из-за этого поручения, сроки и ответственные могут теряться или искажаться. Целевая аудитория MVP — секретари совещаний, руководители и кураторы поручений.

## Целевой сценарий MVP

1. Пользователь загружает аудиозапись совещания.
2. Локальный модуль speech-to-text строит транскрипт на русском, казахском или смешанной речи.
3. Модуль диаризации разделяет реплики по говорящим.
4. Meeting Protocol Agent анализирует транскрипт и извлекает поручения.
5. Для каждого поручения сохраняются ответственный, срок, evidence-фрагмент и признак необходимости ручной проверки.
6. Формируется краткое управленческое саммари.
7. Пользователь просматривает результат и экспортирует итоговый протокол в DOCX.

## Обязательные требования кейса

- распознавание речи участников;
- русский язык;
- казахский язык;
- смешанная русско-казахская речь;
- диаризация;
- поручения с ответственным и сроком;
- итоговое саммари;
- экспорт протокола в DOCX/PDF.

## Приватность

Кейс требует возможности работы в закрытом контуре: аудио и текст совещания не должны передаваться во внешние облачные API.

Поэтому финальный demo-пipeline проектируется local-first/self-hosted.

У команды есть ключи OpenAI и NVIDIA. Ограничение кейса запрещает отправлять аудио и текст совещания в их облачные API, поэтому эти ключи не входят в путь обработки MVP. Модель для анализа транскрипта запускается локально (например, через Ollama). Секреты не коммитятся в Git.

## Контракт данных

Основные модели находятся в `app/models/schemas.py`:

- `TranscriptSegment` — одна реплика с таймкодами и speaker id;
- `ActionItem` — поручение с ответственным, сроком и evidence;
- `SpeakerInfo` — соответствие speaker id и предполагаемого имени;
- `MeetingResult` — итог анализа одного совещания;
- `AgentEvent` — журнал этапов работы агента.

Это общий контракт между тремя ветками разработки.

## Meeting Protocol Agent

Оркестратор находится в `app/agents/meeting_agent.py`.

Файл пока содержит интерфейс с `NotImplementedError`: реализацию должен добавить участник `feature/agent`. Планируемая последовательность инструментов:

```text
Transcript
   |
   +--> speaker resolver
   +--> task extractor
   +--> deadline normalizer
   +--> validator
   +--> summarizer
   |
   v
MeetingResult
```

Архитектура специально допускает замену конкретной локальной модели без изменения UI и STT-pipeline.

## Разделение команды

- `feature/audio` — Audio / STT / diarization;
- `feature/agent` — Meeting Protocol Agent / extraction / validation / summary;
- `feature/ui` — Streamlit / DOCX / integration;
- `main` — общий контракт и место для интеграции; полный сценарий пока не проверен.

## Streamlit UI и DOCX

UI запускается локально в явном demo-режиме или в режиме обработки MP3/WAV:

```powershell
py -3.11 -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements-ui.txt
streamlit run streamlit_app.py
```

В demo-режиме приложение использует синтетический `MeetingResult` и явно помечает его как тестовый.
В режиме локальной обработки UI вызывает `process_audio(audio_path)`, затем
`MeetingProtocolAgent().run(segments, meeting_date, title)`. До появления реализации audio-модуля
приложение показывает ошибку стадии распознавания, не подменяя результат demo-данными.

Перед скачиванием DOCX можно исправить имя говорящего, исполнителя и срок. Экспорт строится из
исправленного `MeetingResult` и содержит название, дату, саммари, поручения, предупреждения и
транскрипт с таймкодами.

## Данные и внешние сервисы

Для демонстрации используются предоставленные организаторами тестовые записи совещаний и отдельный короткий тест смешанной русско-казахской речи.

Внешние AI API не являются частью допустимого финального processing path для аудио/текста совещания из-за требования закрытого контура.

## Сборка трёх веток

Каждый участник сначала подтягивает актуальный `main` в свою ветку и использует `app/models/schemas.py` как единый контракт. Не копируйте схемы по веткам и не меняйте публичные поля без согласования. Подключаемые интерфейсы:

```python
# feature/audio
process_audio(audio_path: str) -> list[TranscriptSegment]
# feature/agent
MeetingProtocolAgent().run(transcript, meeting_date, title) -> MeetingResult
# feature/ui
build_docx(result: MeetingResult) -> bytes
```

При падении диаризации транскрипция должна сохраниться с `speaker_id="UNKNOWN"` и предупреждением. Если локальная LLM не вернула проверяемый ответ, показываем предупреждение и исходный транскрипт: недоказанные поручения не включаем. Каждое поручение должно иметь фрагмент подтверждения, а неуказанные исполнитель и срок остаются `null`. Пустой срок не означает ошибку распознавания: пользователь видит его в таблице.

Для финальной проверки запускаем настоящий путь **MP3 → транскрипт → говорящие → поручения → саммари → DOCX**, затем проверяем отдельно русский, казахский и смешанную речь. Примеры `Совещание №1/№2` служат тестовыми данными вне репозитория. В совещании №2 особенно проверяем поручение Ерлану до конца недели, поиск альтернативного поставщика Ботагоз Нурлановной за две недели и поручения Салтанат Ерболовне без названного срока. Автоматическая разметка говорящих не равна достоверному установлению их имён: сомнительные имена требуют ручной проверки.

Тест `pytest -q` проверяет только общий контракт и локальную конфигурацию. Он **не доказывает**, что аудио, модель агента или экспорт уже работают.
